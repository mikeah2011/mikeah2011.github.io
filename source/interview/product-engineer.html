01 / ARCHITECTURE

Maestro 架構：讓審查結果進入同一條處理流程

先記住這句：Maestro 不增加一個審查者，而是把多方評論整理成可決策、可修復、可停止的流程。

我把它命名為 Maestro，取意於樂團指揮：各個審查機器人像不同聲部，各自提出觀點；Maestro 不取代它們，而是負責整理、去重、協調後續修復，並判斷何時該停止。

CLI 由 LoopOrchestrator 統一調度；目前程式碼中實際落地的平台介接是 GitHub。

02 / REVIEW LOOP

一輪審查怎麼走？意見不一致時怎麼處理？

  1. 收集審查等 CI 與機器人評論，轉成 Finding。
  2. 分類問題規則先判；需要時才交給 LLM。
  3. 決定怎麼處理CLI 建議 fix / defer / reject；人可覆寫，逾時採預設。
  4. 三層去重精確 hash → 標題模糊比對 → 可選的語意比對。
  5. 檢查停止條件追蹤關鍵 Finding 與跨輪變化；震盪、增加或違反不變量時停止／升級。
  6. 修復並回覆小範圍修復、每輪一個 commit，回覆／解決討論串並請機器人複查。
達停止條件：停止並升級人工判斷。 尚未收斂：重跑 CI 與審查，回到 01；最多 3 輪。

三層去重：由便宜、確定到語意判斷

1 · 精確雜湊比對 Finding.hash（檔案、5 行位置區段、分類與內容雜湊）；相同就命中。
→
2 · 模糊比對比較標題的 Levenshtein 正規化相似度；預設門檻 0.8。
→
3 · 語意比對可注入 LLM callback 判斷不同措辭是否同義；每次最多 10 次呼叫。
任一層命中：記錄重複項並指向既有 Finding；三層都未命中：保留為新的 Finding，進入後續處理。

不同意見不靠「哪個機器人票數多」決定。系統先把評論分類，再由 CLI 提供修復／延後／拒絕建議，使用者可以逐項覆寫；跨輪則由收斂監控判斷是否持續重複。每輪最多一個 commit、每個討論串最多回覆一次，避免自動化本身製造更多噪音。

實作範圍說明：Dedup 已提供第三層 LLM 語意比對的 callback 與每次最多 10 次呼叫的限制；目前 CLI 組裝尚未將設定中的 semanticDedup 路由接到這個 callback，因此這一層目前是可擴充介面，不應描述成 CLI 已啟用的功能。
03 / A PRACTICAL AI HABIT

最棘手的問題，以及我平常怎麼讓 AI 幫得上忙

最棘手的是「不同文字是否真的是同一個問題」：比對太嚴格會漏掉重複，合併太積極又會把獨立缺陷或相反建議吞掉。我把它拆成由便宜到昂貴的判斷層，並用固定 hash 與相似度門檻控制成本；對語意邊界情況保留人工決策，且以每輪預算、最多三輪及收斂條件限制副作用。這也讓未接線的語意層成為清楚可驗證的下一步，而不是假設它已經工作。

日常使用上，我會先把專案結構、不可違反的工程規則，以及實際驗證指令寫進 repo 的 CLAUDE.md，再用小範圍 prompt 指定要改的模組、預期行為與測試。這樣不用每次重講架構，也能避免 AI 順手重構不相關程式。

我會這樣下任務
「請先依 CLAUDE.md 理解模組邊界，只處理這次指定的問題；先補上會失敗的測試，再做最小修改。不要改動範圍外檔案。完成後執行 bun run verify，回報測試結果；若證據不足，請標示未知，不要自行補假設。」

這份專案規則包含架構、收斂與防重複操作的不變量，以及固定驗證命令；AI 因此能從一開始就依專案脈絡工作，而不是只按通用最佳實務猜答案。
