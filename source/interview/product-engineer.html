01 / Q1 · 三層去重與意見收斂

Maestro 只做三件事：合併重複、判斷該不該改、決定何時停

CodeRabbit、Copilot、Codex、Ellipsis 在同一個 PR 上會留幾十條意見，很多是同一件事講了三四遍，也有互相矛盾的。Maestro 不額外審查程式碼，只處理這些意見。

去重：三層，從最便宜的開始

  1. 完全一樣。每條意見算一個指紋＝雜湊(檔案 + 行號區間 + 問題類別 + 附近程式碼)，相同就是重複。零成本，先擋掉六成。
  2. 說法不同、標題很像。比較標題的文字相似度，達到 0.8 就當成同一件事，再擋兩成半。
  3. 差很多但意思一樣。交給大模型判斷；這層最貴，一輪最多問 10 次。誠實標註：介面與單測都在，但還沒接上線。

意見不一致：不投票，用規則

  1. 先統一格式。各家機器人的嚴重度用詞不同（critical / blocker / error / fatal），先對到同一把尺，否則無從比較。
  2. 再判是 bug 還是口味。嚴重度關鍵、或碰到認證與支付路徑的算 bug；寫著 nit: 這種字的算口味；規則判不出來，才問大模型。
  3. 類別決定動作。bug 就改，口味先擱著，明顯判斷錯的直接拒絕並附理由。人可以逐條推翻，但 30 秒沒動作就照建議走。

什麼時候停：只看關鍵問題有沒有變少

清零＝完成；越修越多或同一批問題反覆出現＝停，交給人；最多三輪。「關鍵問題」只算真的是 bug、嚴重度 critical／high 以上的那一類。

另有一條硬規矩：它自己不能變成噪音——每輪只准一次提交、每條意見只回覆一次，違反就直接崩掉，而不是警告一聲繼續跑。

02 / Q2 · 最棘手的問題

測試全綠，但功能其實沒生效

註解寫著「指紋取自附近程式碼，不是評論文字，所以換種說法也認得出同一個問題」（ConvergenceMonitor.ts:173-186），單測逐條驗證、全部通過；但實際跑起來，跨機器人的重複一條都沒合併掉。

怎麼找到

  1. 看紀錄。去重結果按層記了數（exact／fuzzy／llm），但對外發的事件只報了加總（LoopOrchestrator.ts:335）。把三層拆開看，第一層的命中率遠低於預期，合併幾乎全落在第二層。
  2. 往回追指紋在哪算出來。整個倉庫只有一個地方呼叫它，而那個呼叫的第四個參數名叫「附近程式碼」，傳進去卻是機器人寫的評論文字（LoopOrchestrator.ts:616）。
  3. 確認設計沒接上。該放程式碼片段的欄位，全倉庫找不到任何賦值的地方——不是筆誤，是整條設計在組裝時斷了。

後果：傳進去的是評論文字，措辭一改指紋就跟著變，第一層永遠認不出跨機器人的同一個問題。

怎麼修

  1. 把「位置」和「語意」兩種指紋拆開。還沒分類之前，不該假裝知道問題類別。
  2. 真的從 diff 裡取出附近程式碼，填進那個欄位，讓它不再只是型別上的裝飾。
  3. 補一條從入口跑的測試：同一個位置、不同措辭 → 去重後只剩一個。

這一項我還沒收口，所以寫的是「怎麼找到、打算怎麼修」。倉庫是公開的，上面那三個連結點進去，現在還是這個樣子。它改變了我的習慣：註解宣稱一個系統性質，就要有一條從呼叫入口驗證它的測試。

03 / Q3 · 日常 AI 開發的具體做法

靠的不是神奇 prompt，是兩樣留在倉庫裡的東西

一、把專案規矩寫進倉庫裡的規則檔

倉庫根目錄的 CLAUDE.md 只放三類內容：驗證命令、模組邊界、不讓步的硬規則。

# CLAUDE.md（節錄） ## 常用指令 bun run verify # 型別檢查 + 測試；提交前的驗證口徑寫死在這裡 ## 關鍵設計決策 · 每輪的分類、提交、回覆都有配額，溢出時 throw，不准 warn-and-continue · 所有副作用（onFix、onCommit、sleep）都從建構函式注入，測試中可以替換掉 · 未設定的環境變數必須寫成 ${VAR:-預設值}

二、每次任務只圈一個小範圍

我實際會這樣下：「請先依 CLAUDE.md 理解模組邊界，這次只處理 core/dedup 這一層；先在 tests/core/dedup/ 補一個會失敗的測試，再做最小修改讓它通過。不要改到範圍外的檔案，不要把 throw 改成警告。完成後跑 bun run verify，回報實際輸出；證據不足的地方標為未知，不要自己補假設。」

讓 AI 改程式碼的 prompt 更嚴：固定 JSON 輸出、溫度 0、信心不足 0.7 直接丟掉、只給目標行上下 20 行——不讓它假裝看過整個檔案。

兩樣合起來是同一件事：把架構事實、驗證口徑、不讓步的底線，變成倉庫裡可以 diff、可以 review 的檔案，而不是每次對話都要重講的個人記憶。
