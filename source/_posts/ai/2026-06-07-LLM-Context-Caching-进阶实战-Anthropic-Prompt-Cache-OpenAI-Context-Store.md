# LLM Context Caching 进阶实战：Anthropic Prompt Cache + OpenAI Context Store——系统提示复用、KV Cache 共享与成本直降 90%

## 一、为什么 LLM 上下文处理如此昂贵？

在生产环境中构建 LLM 应用时，开发者最直观的感受就是：**Token 消耗速度快得惊人**。以 Claude Sonnet 4 为例，输入 Token 价格为每百万 Token 三美元，输出为每百万 Token 十五美元。一个包含八千 Token 系统提示的智能体应用，每次对话轮次都要重新传输这八千个 Token——如果每天处理十万次请求，仅系统提示的输入成本就达到每天两千四百美元，一个月下来超过七万美元。

更糟糕的是，每次请求都需要**重新计算**这八千个 Token 的键值缓存。Transformer 架构的自注意力机制要求对每个 Token 计算查询向量、键向量和值向量，这部分计算量与 Token 数量呈二次方关系。对于长系统提示（超过一万个 Token），首 Token 延迟可能高达三到五秒，严重影响用户体验。

**核心痛点总结如下：**

首先是经济成本问题：重复 Token 的传输和计费造成严重浪费。在传统的无缓存模式下，每次 API 调用都会将系统提示的全部内容作为输入 Token 进行计费，无论这些内容是否在上一次调用中已经处理过。对于拥有大型知识库或复杂角色设定的应用，系统提示动辄数千甚至数万 Token，累积的费用令人咋舌。

其次是计算延迟问题：键值缓存的重复计算拖慢响应速度。在 Transformer 的自注意力机制中，每个 Token 都需要计算查询、键、值三个向量，而键向量和值向量的维度通常在数千的量级。对于一个八千 Token 的系统提示，每次请求都需要执行数百万次浮点运算来重新生成这些缓存，这直接导致首 Token 延迟大幅增加。

最后是架构复杂度问题：开发者需要自行管理上下文的缓存与失效策略。在没有官方缓存 API 的情况下，许多开发者尝试在应用层实现自己的缓存逻辑，但这不仅增加了代码复杂度，还无法真正避免服务端的重复计算——因为 LLM 提供商的计费和计算是绑定在一起的。

二零二四到二零二五年，Anthropic 和 OpenAI 相继推出了服务端上下文缓存 API，将这个问题从应用层下沉到基础设施层，从根本上解决了重复计算的瓶颈。本文将深入剖析这两大平台的缓存机制，结合 Laravel 应用的实际场景，提供完整的生产级集成方案。

## 二、Transformer 键值缓存技术原理

要理解上下文缓存的价值，必须先深入理解 Transformer 的键值缓存机制。

### 2.1 自注意力机制的计算流程

在 Transformer 的每一层中，输入序列的每个 Token 都需要计算三个向量。查询向量表示当前 Token 想要关注什么信息，键向量表示当前 Token 能提供什么信息，值向量则承载了当前 Token 的实际语义内容。这三个向量通过矩阵乘法从输入嵌入中生成，其中权重矩阵在训练完成后就固定了。

注意力计算的核心公式是：注意力权重等于查询向量与键向量的点积经过缩放和软归一化后，再与值向量相乘。这意味着每个 Token 的输出都是所有历史 Token 的值向量的加权和，权重由查询向量和键向量的相似度决定。

每次生成新 Token 时，模型都需要对**所有**历史 Token 进行上述注意力计算。对于一个包含八千个 Token 的系统提示，即使用户只输入了一句话，模型也必须处理全部八千个 Token 的注意力计算。

### 2.2 键值缓存的优化原理

键值缓存的核心洞察非常简单：**如果输入的前缀没有变化，那么这些 Token 的键向量和值向量也不会变化**。因此，我们可以将这些前缀的键值向量缓存起来，在后续请求中直接复用，只需要计算新 Token 的键值向量。

没有键值缓存时，每次请求都需要对系统提示和用户输入的全部内容进行全量计算。而有了键值缓存后，系统提示的键值向量从缓存中加载，几乎不消耗计算资源，只需要对用户输入的新内容进行增量计算。

这种优化的实际效果非常显著。对于一个包含八千 Token 系统提示加五百 Token 用户输入的请求：没有缓存时，需要计算八千五百个 Token 的全量键值向量，首 Token 延迟约三秒；而有了缓存后，只需复用八千个 Token 的缓存键值并计算五百个新 Token 的键值，首 Token 延迟降至约零点五秒。延迟降低了百分之八十以上，同时服务端不需要为缓存的 Token 重复计费。

## 三、Anthropic 提示缓存机制详解

### 3.1 工作原理

Anthropic 的提示缓存是一个自动化的前缀缓存机制。它的工作原理是：当新的 API 请求到达时，服务端会将其输入内容与最近的缓存条目进行前缀比较。如果新请求的前 N 个 Token 与某个缓存条目的前缀完全一致，则可以复用该缓存条目的键值向量，跳过这些 Token 的计算过程。

缓存的关键规则如下。第一，前缀匹配：只有当新请求的前 N 个 Token 与之前缓存的前缀完全一致时，才能命中缓存。任何前缀中的字符变化（包括空格、换行符、标点符号的差异）都会导致缓存失效。第二，缓存有效期：缓存条目在创建后五分钟内有效，每次命中会刷新生存时间。这意味着只要在五分钟内有新的请求命中了缓存，该缓存条目就会续期。第三，最小缓存单元：最少一千零二十四个 Token 才会被缓存。短于这个长度的前缀不会触发缓存机制。第四，缓存位置：仅缓存系统提示和工具定义，不缓存用户消息和助手回复。这是因为系统提示在连续对话中保持稳定，而用户消息和助手回复每次都不同。

### 3.2 显式缓存控制

除了自动缓存检测外，Anthropic 还支持通过 `cache_control` 参数显式声明缓存控制。在系统提示的文本块中添加 `cache_control` 字段，可以告诉服务端将该部分内容标记为缓存候选。这种方式适用于需要精确控制缓存范围的场景，比如将大段参考文档拆分为多个缓存块。

### 3.3 响应中的缓存指标

Anthropic 在响应的使用量统计字段中返回缓存相关的 Token 统计信息。缓存创建输入 Token 表示首次缓存创建消耗的 Token 数量，这些 Token 按正常价格计费。缓存读取输入 Token 表示从缓存中读取的 Token 数量，这些 Token 仅收取正常输入价格的百分之十。普通输入 Token 则表示既未被缓存也未被创建缓存的普通输入内容。

通过监控这三个指标，开发者可以精确了解缓存的使用情况。例如，如果缓存创建 Token 持续很高而缓存读取 Token 很低，说明缓存命中率不佳，需要排查系统提示是否频繁变化。

## 四、OpenAI 上下文缓存 API

### 4.1 自动缓存机制

OpenAI 从二零二四年底开始引入了自动前缀缓存机制，与 Anthropic 的原理类似但实现细节有所不同。OpenAI 的自动缓存对所有 GPT-4o、GPT-4o-mini 和 GPT-4.1 系列模型生效，无需额外配置。

OpenAI 的缓存规则如下。缓存有效期约为五到十分钟，比 Anthropic 的五分钟稍长。缓存命中时，输入 Token 价格享受百分之五十的折扣，这比 Anthropic 的百分之九十折扣力度要小，但对于使用 OpenAI 的开发者来说仍然是显著的成本节省。缓存的检测和复用完全自动进行，开发者不需要在 API 请求中添加任何特殊参数。

### 4.2 响应中的缓存指标

OpenAI 在响应的使用量统计字段中包含一个缓存 Token 字段，表示从缓存读取的 Token 数量。开发者可以通过比较这个值与总输入 Token 数量来计算缓存命中率。

### 4.3 存储 API 与持久化缓存

OpenAI 还推出了一项名为存储的功能，允许开发者创建持久化的会话上下文。存储 API 可以保存对话历史和上下文信息，在后续请求中自动加载。虽然这不是严格意义上的键值缓存，但它为需要跨会话保持上下文的应用提供了便利。存储 API 目前处于测试阶段，适用于需要长期记忆的对话应用。

## 五、系统提示复用策略与最佳实践

### 5.1 提示结构设计的黄金法则

**核心原则：稳定内容放在前面，动态内容放在后面。**

在构建系统提示时，应该按照内容的稳定性进行分层。最底层（最前面）是完全稳定的内容，包括角色定义、编码规范、项目上下文等，这些内容在应用的整个生命周期中都不会变化。中间层是半稳定的内容，比如 API 文档、数据库模式定义等，这些内容可能偶尔更新，但更新频率远低于请求频率。再往上是动态内容，比如用户的历史对话摘要、当前会话的状态信息等，这些内容每次请求都可能不同。最顶层（最后面）是用户的具体消息，这是每次请求都会完全变化的内容。

这种分层结构确保了稳定内容始终位于输入的最前面，最大化了缓存命中率。在实际应用中，只要系统提示的前八千个 Token 保持不变，缓存命中率就能达到百分之九十以上。

### 5.2 避免缓存失效的常见陷阱

在实际开发中，有很多看似无害但会破坏缓存前缀一致性的做法。首先是时间戳：如果在系统提示中嵌入了当前时间戳，每次请求的前缀都会变化，完全无法命中缓存。解决方法是将时间戳放在用户消息中，而不是系统提示中。其次是会话标识符：将用户或会话的唯一标识放在系统提示中会破坏前缀匹配。解决方法是将这些标识放在用户消息中传递。再次是随机内容：在系统提示中使用随机数或 UUID 会导致每次前缀都不同。最后是模板变量：使用 Blade 模板或其他模板引擎渲染系统提示时，如果模板变量的值每次不同，会导致前缀变化。解决方法是确保模板变量的值在缓存有效期内保持稳定。

### 5.3 Laravel 缓存管理器实现

在 Laravel 应用中，我们需要一个专门的缓存管理器来协调 LLM 缓存与应用缓存。这个管理器需要处理以下职责：监控缓存即将过期的时间点，在过期前主动发起刷新请求；管理系统提示的版本号，当提示内容变更时平滑过渡到新版本；验证系统提示的缓存就绪状态，确保没有动态内容破坏前缀一致性；记录每次请求的缓存命中指标，为后续优化提供数据支持。

缓存管理器的核心逻辑是基于 Laravel 的缓存门面实现的。它将系统提示按提供商和版本号进行缓存，在二十四小时内有效。当需要更新系统提示时，通过版本号机制确保旧版本的缓存自然过期，新版本的缓存被创建。

## 六、成本分析：真实数字对比

### 6.1 场景设定

以一个日均十万次请求的 AI 客服系统为例。系统提示包含八千个 Token，涵盖角色定义、业务规则、知识库摘要等内容。用户输入平均五百个 Token，包括问题描述和上下文信息。AI 输出平均八百个 Token，包含回答和推理过程。

### 6.2 Anthropic 成本计算

在没有缓存的情况下，每次请求的输入成本为八千五百个 Token 乘以每百万 Token 三美元的价格，即每次请求零点零二五五美元。十万次请求的每日输入成本为两千五百五十美元。输出成本为每次请求八百个 Token 乘以每百万 Token 十五美元，即每次请求零点零一二美元，每日输出成本为一千二百美元。每日总成本为三千七百五十美元。

在启用缓存且命中率为百分之八十的情况下，八千个系统提示 Token 中有六千四百个可以命中缓存，仅收取百分之十的价格。用户输入的五百个 Token 按正常价格计费。每日输入成本降至约三百九十美元，输出成本保持不变为一千二百美元。每日总成本降至一千五百九十美元，节省百分之五十七点六。每月节省约六万四千八百美元。

需要注意的是，首次请求时缓存创建 Token 按正常价格计费，后续命中才享受折扣。因此在应用刚启动或缓存过期后的首次请求中，成本与无缓存模式相同。

### 6.3 OpenAI 成本计算

在没有缓存的情况下，每次请求的输入成本为八千五百个 Token 乘以每百万 Token 二美元的价格，即每次请求零点零一七美元。十万次请求的每日输入成本为一千七百美元。输出成本为每次请求八百个 Token 乘以每百万 Token 八美元，即每次请求零点零零六四美元，每日输出成本为六百四十美元。每日总成本为两千三百四十美元。

在启用缓存且命中率为百分之八十的情况下，缓存命中的 Token 享受百分之五十折扣。每日输入成本降至约九百美元，输出成本保持不变为六百四十美元。每日总成本降至一千五百四十美元，节省百分之三十四点二。每月节省约两万四千美元。

### 6.4 综合成本节省分析

总成本节省并不仅仅来自 Token 价格的折扣，还包括以下几个方面。第一是传输成本的减少：缓存命中时不需要重新传输系统提示的全部字节，对于八千个 Token 的系统提示，每次请求可以节省约三十二千字节的有效载荷。第二是首 Token 延迟的降低：从三到五秒降至零点五到一秒，用户体验显著提升。第三是吞吐量的提升：服务端计算资源更高效地利用，间接提升了并发处理能力。第四是带宽的优化：对于高并发应用，减少的网络传输量可以降低基础设施成本。

## 七、生产部署注意事项

### 7.1 提示结构优化清单

在部署到生产环境之前，需要对系统提示进行缓存就绪性验证。验证内容包括：检查系统提示的 Token 数量是否达到最小缓存阈值（一千零二十四个 Token）；检测是否存在模板变量或动态内容；检查是否包含时间戳或其他每次变化的内容；验证前缀部分在连续请求中保持完全一致。

### 7.2 监控与告警策略

在生产环境中，需要建立完善的监控体系来跟踪缓存的健康状况。关键指标包括：缓存命中率（目标值：百分之八十以上）、首 Token 延迟（目标值：一秒以内）、缓存创建与读取的 Token 比例、以及每次请求的成本变化趋势。当缓存命中率低于百分之六十时，应该触发告警并排查原因。常见的原因包括系统提示中引入了动态内容、缓存有效期过短导致频繁失效、以及并发请求过多导致缓存条目被挤出。

### 7.3 多提供商切换策略

在 Laravel 应用中，可以通过策略模式实现多提供商的无缝切换。当一个提供商的缓存命中率下降或服务不可用时，自动切换到另一个提供商。切换逻辑应该考虑以下因素：缓存折扣力度（Anthropic 的百分之九十折扣优于 OpenAI 的百分之五十折扣）、缓存有效期（OpenAI 的五到十分钟有效期略长于 Anthropic 的五分钟）、以及 API 的可用性和延迟表现。

### 7.4 灰度发布与回滚策略

在引入缓存机制时，建议采用灰度发布策略。首先在非关键路径上测试缓存效果，监控命中率和成本变化。确认效果稳定后，逐步扩展到所有 API 调用。如果发现缓存导致了异常行为（比如模型回复了过时的信息），可以快速回滚到无缓存模式。回滚逻辑应该能够在配置层面一键切换，不需要修改代码。

## 八、Anthropic 与 OpenAI 缓存方案对比

Anthropic 的提示缓存提供百分之九十的输入价格折扣，是目前市场上最激进的缓存优惠。它支持显式的缓存控制参数，允许开发者精确管理缓存范围。缓存有效期为五分钟，每次命中自动续期。适用于对成本极度敏感且需要精细控制的应用场景。

OpenAI 的自动缓存提供百分之五十的输入价格折扣，力度相对温和。它完全自动运行，不需要任何额外配置。缓存有效期为五到十分钟，略长于 Anthropic。适用于追求简单易用且已经深度集成 OpenAI 生态的应用场景。

从技术实现角度看，两者都基于前缀匹配的键值缓存原理，核心差异在于折扣力度、有效期长短和 API 控制能力。在实际选型时，建议根据应用的成本结构、性能需求和团队的技术栈偏好进行综合评估。对于新项目，可以同时集成两个提供商，通过抽象层实现灵活切换。

## 九、进阶技巧与深度优化

### 9.1 系统提示分块缓存

对于包含大量参考文档的应用，可以将系统提示分为多个缓存块。每个块都有独立的缓存控制声明，这样即使某个块的内容发生变化，其他块仍然可以命中缓存。这种方法特别适用于知识库问答系统，其中核心规则部分保持稳定，而领域知识部分可能频繁更新。

### 9.2 工具定义缓存

在使用函数调用或工具使用的场景中，工具定义通常是最大的 Token 消耗源之一。将工具定义放在系统提示中并利用缓存机制，可以显著降低连续对话的成本。Anthropic 的缓存机制会自动检测工具定义的前缀匹配，因此只需要确保工具定义在请求中保持稳定顺序即可。

### 9.3 对话历史的渐进式缓存

在长对话场景中，可以采用渐进式缓存策略。将对话历史按时间分段，最近的几轮对话保持在缓存中，而较早的对话则通过摘要替代。这样既保持了对话的连贯性，又控制了输入 Token 的数量。在 Laravel 中，可以使用 Redis 的有序集合来管理对话历史的分段和过期。

### 9.4 预热缓存

对于新部署的应用或缓存过期后的首次请求，可以通过预热缓存来避免冷启动延迟。预热的原理是：在应用启动时发送一个模拟请求，使服务端创建缓存条目。后续的真实请求就可以命中这个预热的缓存。在 Laravel 中，可以在服务提供者的引导方法中触发预热逻辑。

## 十、总结

LLM 上下文缓存不是锦上添花的优化，而是**生产环境中控制成本和提升性能的基础设施级能力**。它从根本上解决了 Transformer 架构中键值缓存重复计算的问题，将首 Token 延迟降低了百分之八十以上，将输入成本降低了百分之五十到九十。

在 Laravel 项目中实现上下文缓存并不复杂，核心只需要把握两个原则。第一是保持系统提示的稳定性：将所有不经常变化的内容放在系统提示的最前面，确保连续请求的前缀完全一致。第二是监控缓存命中指标：通过分析缓存读取和创建的 Token 比例，及时发现并解决缓存失效的问题。

在成本控制方面，以日均十万次请求、八千 Token 系统提示的场景为例，Anthropic 的缓存机制每月可以节省超过六万美元，OpenAI 的缓存机制每月可以节省超过两万美元。这种成本节省幅度对于任何规模化运营的 LLM 应用来说都是不可忽视的。

展望未来，随着更多提供商推出缓存 API，上下文缓存将成为 LLM 应用开发的标准实践。开发者需要从架构设计阶段就考虑缓存的友好性，将缓存策略纳入应用的核心设计中，而不是事后优化。掌握上下文缓存的原理和实践，将是每一位 LLM 应用开发者的核心竞争力之一。

## 十一、SDK 代码示例

### 11.1 Anthropic Python SDK（显式缓存控制）

```python
import anthropic

client = anthropic.Anthropic(api_key="sk-ant-xxx")

SYSTEM_PROMPT = """
你是公司的 AI 客服助手，负责回答用户关于产品使用、订单查询和退款流程的问题。
以下是公司的核心业务规则……（此处省略数千 Token 的业务文档）
"""

def ask_support(user_message: str, conversation_history: list[dict]):
    """带缓存控制的客服对话请求"""
    response = client.messages.create(
        model="claude-sonnet-4-20250514",
        max_tokens=1024,
        system=[
            {
                "type": "text",
                "text": SYSTEM_PROMPT,
                "cache_control": {"type": "ephemeral"},  # 显式声明缓存
            }
        ],
        messages=conversation_history + [{"role": "user", "content": user_message}],
    )

    # 解析缓存指标
    usage = response.usage
    print(f"输入 Token: {usage.input_tokens}")
    print(f"缓存创建 Token: {usage.cache_creation_input_tokens}")
    print(f"缓存读取 Token: {usage.cache_read_input_tokens}")

    return response.content[0].text
```

### 11.3 OpenAI Python SDK（自动缓存）

```python
from openai import OpenAI

client = OpenAI(api_key="sk-xxx")

SYSTEM_PROMPT = """
你是公司的 AI 客服助手……（数千 Token 的业务文档）

def ask_support_openai(user_message: str, conversation_history: list[dict]):

        model="gpt-4o",

            {"role": "system", "content": SYSTEM_PROMPT},
            *conversation_history,

    usage = response.usage

    print(f"缓存命中 Token: {usage.prompt_tokens_details.cached_tokens}")

    return response.choices[0].message.content
```

## 十三、成本节省计算详解

### 13.1 计算公式

**无缓存时的每日输入成本：**

```
每日输入成本 = 日请求量 × 总输入 Token / 1,000,000 × 输入单价
```

**有缓存时的每日输入成本：**

```
每日输入成本 = 日请求量 × [
  缓存命中 Token / 1,000,000 × 输入单价 × 缓存折扣率
  + 缓存未命中 Token / 1,000,000 × 输入单价
]
```

### 13.2 实际计算示例

以 Anthropic Claude Sonnet 4（输入 $3/M tokens）为例：

| 参数 | 值 |
|------|-----|
| 日请求量 | 100,000 |
| 系统提示 | 8,000 tokens |
| 用户输入 | 500 tokens |
| 缓存命中率 | 85% |
| 缓存折扣 | 90%（即缓存读取价格 = 原价 × 0.1） |

**无缓存：**
- 每日输入成本 = 100,000 × 8,500 / 1,000,000 × $3 = **$2,550/天**

**有缓存：**
- 缓存命中 Token = 8,000 × 85% = 6,800
- 缓存未命中 Token = 8,500 − 6,800 = 1,700
- 每日输入成本 = 100,000 × (6,800 / 1,000,000 × $3 × 0.1 + 1,700 / 1,000,000 × $3)
- = 100,000 × ($0.00204 + $0.0051)
- = 100,000 × $0.00714 = **$714/天**

**每日节省 $1,836，月节省 $55,080，节省率 72%。**

### 13.3 不同缓存命中率下的成本对比

| 缓存命中率 | Anthropic 每日输入成本 | OpenAI 每日输入成本 | 月节省（Anthropic） | 月节省（OpenAI） |
|-----------|----------------------|--------------------|--------------------|-----------------|
| 0% | $2,550 | $1,700 | $0 | $0 |
| 50% | $1,335 | $1,275 | $36,450 | $12,750 |
| 70% | $876 | $1,105 | $50,220 | $17,850 |
| 85% | $714 | $1,017 | $55,080 | $20,490 |
| 95% | $648 | $974 | $57,060 | $21,780 |

> **结论：** Anthropic 在高缓存命中率下的成本优势极为显著。当命中率超过 70% 时，Anthropic 的输入成本仅为 OpenAI 的约 70%。

## 十四、常见陷阱与排错指南

### 14.1 缓存永远不命中的排查清单

**症状：** 监控显示 `cache_read_input_tokens` 始终为 0。

排查步骤：

1. **检查 Token 数量**：系统提示是否达到最小缓存阈值（Anthropic: 1,024 tokens，OpenAI: 102 tokens）？
2. **检查前缀稳定性**：系统提示中是否包含时间戳、UUID、随机数或会话 ID？使用 `diff` 工具对比连续两次请求的系统提示，找出差异。
3. **检查模板渲染**：Blade/Jinja/ERB 模板是否在每次渲染时产生了不同的输出？将渲染结果 dump 到日志中进行比对。
4. **检查请求间隔**：两次请求之间是否超过了缓存有效期？在低流量场景下（请求间隔超过 5 分钟），缓存必然失效。
5. **检查消息顺序**：系统提示中的文本块顺序是否在请求之间保持一致？任何顺序变化都会破坏前缀匹配。

### 14.2 缓存命中后模型输出异常

**症状：** 缓存命中后，模型引用了过时的知识或忽略了最新的系统提示更新。

**原因：** 系统提示更新后，旧版本的缓存仍在有效期内。模型使用的是旧缓存的键值向量，而非新版本的内容。

**解决方案：**
- 更新系统提示时，修改其前缀内容（例如在开头添加版本注释），强制创建新的缓存条目。
- 使用版本号机制管理提示更新，配合应用层缓存管理器实现平滑过渡。
- 在紧急情况下，等待 5–10 分钟让旧缓存自然过期。

### 14.3 缓存导致的并发问题

**症状：** 在高并发场景下，缓存命中率不稳定，波动较大。

**原因：** 当短时间内有大量不同内容的请求时，服务端的缓存条目可能被频繁替换，导致有效缓存被挤出。

**解决方案：**
- 确保高并发请求的系统提示完全一致（这本身就是最佳实践）。
- 对于多租户应用，将共享的系统提示部分前置，将租户特定内容后置。
- 监控并发请求的系统提示前缀差异，及时发现并修复不一致。

### 14.4 成本反而增加的情况

**症状：** 启用缓存后，账单不降反升。

**可能原因：**
- **首次缓存创建成本**：每次缓存创建的 Token 按正常价格计费。如果系统提示频繁变化导致缓存不断重建，创建成本可能超过节省的成本。
- **最小 Token 限制**：如果系统提示恰好在最小阈值附近，缓存效率可能很低。
- **错误的监控解读**：将缓存创建 Token 误认为缓存命中 Token，导致误判缓存效果。

**解决方案：** 仔细分析 `usage` 字段中的三个 Token 类型，确保正确区分缓存创建和缓存读取的成本。
